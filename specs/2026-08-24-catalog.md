# Catalog (rooms kernel)

**Status**: Workshop draft — first module spec

Parent: [greenfield integrated system](2026-08-24-integrated-system.md). This is the **target** catalog (year-round tables in the one Postgres, not a second database). First event that must run on it: BMT 2026 (2026-11-14). Prototype columns in this git repo do not constrain the model.

Correct slightly-off details here in workshop; do not reopen “day-of never writes catalog.”

## Problem

The capacity spreadsheet is the kernel of every other module. If HQ, volunteers, maps, and the allocator each invent their own DWIN155, we lose. The catalog must be easy to type in by hand, grow a new field without a deploy, and stay untouched on Saturday. It is used **rarely**, so it lives on **`roomsdb.berkeley.mt`** (not `catalog.berkeley.mt`), not as a tab on the planner.

## Decisions (this spec)

| Topic | Decision |
| ----- | -------- |
| Who writes | **Google** + `can_open_ops`. Bookmark **`roomsdb.berkeley.mt`** (not a tab on the planner or HQ). Organizer view-only is a later flag. Day-of tools never `UPDATE rooms`. |
| Identity | Building **code** chosen at **create**, then **read-only** in the catalog form. Pretty **name** (Dwinelle Hall) stays editable. Room **name** (`155`) is editable (also a join key — see below). Display `{code}{roomName}` → `DWIN155`. |
| Codes (seed) | Dwinelle **DWIN**, Wheeler **WHLR**, VLSB **VLSB**, Martin Luther King Jr. Building **MLK**. No GPBB. |
| Built-in facts | `capacity` required integer **≥ 0** (0 allowed for HQ/merch). `is_active`. Optional `sort_order`. |
| All other facts | **Admin-defined fields** (number / text / yes-no), values per room. |
| Room type | **Seed** a custom field `Room type` with choices auditorium / small / large. Admins may rename or delete. |
| Grid pollution | **Still open:** checkbox vs kind dropdown (see Q2). Either way, some rows are not allocator columns. |
| Entry | **Manual** in the catalog UI. No spreadsheet importer required for v1. |
| Soft delete | `is_active = false` retires a room from pickers. Does **not** mean “closed today.” |
| Floor labels | Strings (`C`, `D`, `E`, `B`, `1`, `2`). Dwinelle floors must be the real codes (`C`/`D`/`E`) before map join. |

## Model

```text
buildings        id, code, name, address?, is_active, sort?
floors           id, building_id, label, sort_order
rooms            id, building_id, floor_id?, name, capacity,
                 appears_on_grid, is_active, sort_order?
room_field_defs  id, name, value_type (number|text|boolean), sort_order
room_field_values room_id, field_def_id, value (JSONB)
```

Field defs are global (one org). No tenant table required for v1.

**Identity vs casual edits:** `buildings.code` is a **join key** (grid labels, roster CSV, Figma import, room-login username `DWIN155`). It is **not** a field like capacity.

- **Create building:** admin types code + pretty name (`DWIN` / Dwinelle Hall). Code is required, unique, short (e.g. 2–8 letters).
- **Edit building:** pretty name, address, active — **not** the code. Show the code as text, not an input.
- **v1:** no “rename code” in the UI. Wrong code → create the right building and move rooms, or a one-off SQL/admin fix. A later **Change code** action (confirm + rewrite display) is optional after Nov 14.

Room **name** (`155`) is also a join key but people fix typos more often; keep it editable on the room form. Changing it after a day plan is imported does **not** rewrite the frozen plan (catalog never writes day-of; the plan already copied ids). New imports/CSV matching use the new name.

**If we made the code editable anyway** (admin changes `DWIN` → `DWNL` on Saturday or in October):

| Still works | Breaks or gets confusing |
| ----------- | ------------------------ |
| Postgres FKs: rooms, allocations, assignments, timers all use `building_id` / `room_id` UUIDs | **Human labels** that are computed live: grid headers, HQ list, public “DWIN155”, print *if regenerated* |
| Frozen day-plan **rows** (they store room UUIDs) | **Room-login username** if it is `{code}{name}` typed on the projector laptop — printed packet still says `DWIN155`, laptop must type `DWNL155` |
| Volunteer assigned to that room UUID | **Roster CSV / Figma import** matching on the string `DWIN` until the mapper grows an alias |
| | **URLs** like `#/maps/DWIN/D` and any bookmark or radio shorthand |
| | **Two buildings cannot share a code** — rename collides if `DWNL` exists |
| | People and paper: signs, run-of-show, “go to DWIN155” in Slack |

Nothing in the database “orphans” Dwinelle 155. The cost is **every string that is not the UUID**.

Making it editable is reasonable if we also do at least one of:

1. **Confirm dialog** (“this changes every DWIN155 label and room login”).
2. **Keep old codes as aliases** so CSV, Figma, and login still accept `DWIN` after the display code is `DWNL`.
3. **Snapshot the login username** on day-plan import so Saturday’s projectors do not move when someone edits the catalog (aligned with “day-of does not depend on catalog writes”).

**Code aliases** (if we add them): one **canonical** `code` (what we print and show) plus `aliases[]` (old or alternate strings that still resolve to the same building). Lookup: `DWIN` OR `DWNL` → same `building_id`. Display always uses canonical.

| Helps | Costs |
| ----- | ----- |
| CSV / Figma / search / room login can still use `DWIN` after the label becomes `DWNL` | **Uniqueness is global across codes and aliases.** `DWIN` cannot be another building’s code *or* alias. You cannot recycle `DWIN` for a new hall until you delete the alias |
| Safer to allow a confirmed rename | **Two names in the wild.** HQ screen says `DWNL155`, printed packet and habit still say `DWIN155`. Support (“I logged in as DWIN155”) needs to know they are the same room |
| Matches how people already mix WHLR / Wheeler / WHEE | **Every ingest path must use the same resolver.** Miss the volunteer CSV or a map URL and you get a silent miss, not a FK error |
| URLs can accept old `#/maps/DWIN/D` and 301/redirect to canonical | **Aliases accumulate.** Need UI to add/retire them. Retired too early → CSV breaks; kept forever → namespace pollution |
| | **Does not update paper** or people. Only software inputs. |
| | **Does not replace a Saturday snapshot** if live labels follow canonical: HQ still flips to `DWNL155` the moment you rename, even if login still accepts `DWIN155` |
| | Weak extra login surface (more accepted usernames). Minor compared to “room numbers are public” |

Aliases solve **matching**. They do not solve **one true label**. If the goal is “never surprise projectors on Saturday,” snapshot the login id on plan import (option 3) whether or not you have aliases.

**v1:** skip aliases. Four buildings, codes chosen once (`DWIN`, `WHLR`, `VLSB`, `MLK`). Add aliases when you first need a rename or a second spelling on a CSV. Room-level aliases (`22A` / `22AA`) are a separate, already-planned map concern.

**Capacity vs custom number fields:** the allocator and proctor-count heuristic use built-in `capacity` unless a field is explicitly chosen later (e.g. “guts capacity”). v1 heuristic = built-in `capacity`. Guts can be a custom field staff fill; wiring the heuristic to it is a later checkbox, not a new column type.

**`appears_on_grid`:** the allocator room picker and bulk “all of Dwinelle D” skip false. Maps, volunteer assignment, public labels may still use the row. Timers never apply unless the **day plan** has a testing activity there (ops rooms should not get testing allocations).

**Room type:** seed a custom field with auditorium / small / large (workshop Q1). **Optimal capacity:** a custom number field if staff add it. No leftover tag list.

## Screens (admin)

- Building list / create / edit (code **only on create**, then name/active).
- Floors under a building (label, sort).
- Room list filterable by building/floor/active/appears_on_grid.
- Room form: name, floor, capacity, appears_on_grid, active, plus a **dynamic** section from field defs.
- **Field definitions** admin: add/rename/reorder fields (delete only if unused, or hide).
- If there is an organizer role: same lists, **no save**. Staff who can open ops can write.

No day-of “closed” checkbox here.

## API (shape)

Staff-with-write for mutations. Session required.

- CRUD buildings, floors, rooms, including `appears_on_grid` and field values.
- CRUD `room_field_defs`; values on room update as `fields: { "Guts capacity": 80 }`.
- Inactive room: cannot add to a **new** draft-plan column. Already-imported day plans ignore catalog edits until re-import (day-of overlay, not this module).

JSON camelCase.

## Workshop questions (catalog only)

These are **only** about the rooms database UI and fields, not the grid, not day-of, not Figma.

### 1. Keep today’s `room_type`, or throw it away?

**Locked: B.** Seed a custom field “Room type” with auditorium / small / large. Not a hardcoded column. Grid type-mismatch warning is optional later.

### 2. What is a “kind dropdown”? (still open)

This is **only** the control on the **add/edit room form** that means “does this row become a column on the time×room grid?”

Imagine editing Dwinelle 155. Two possible UIs that store the same idea:

**Checkbox (one bit):**

```text
Name          155
Capacity      481
[x] Show on allocator grid
```

HQ or “merch in 10 Evans” would be the same form with the box **unchecked**. Volunteers and maps can still use that row. The grid will not.

**Kind dropdown (a label that implies that bit):**

```text
Name          155
Capacity      481
Kind          [ Classroom          ▼ ]
              Classroom   → on the grid
              Ops         → not on the grid (HQ, grading, scanning)
              Other       → not on the grid (food, merch)
```

“Kind” here is **not** Figma’s classroom/bathroom/stair colors, and **not** auditorium/small/large. It is a staff-facing folder: classroom vs ops vs other. Internally we can still store `appears_on_grid = (kind == classroom)`.

**Pick checkbox** if you do not care to filter “all HQ rooms” in the catalog list. **Pick dropdown** if you want that filter without inventing a custom field for it.

**How to answer:** `checkbox` or `dropdown` (and the labels if dropdown).

### 3. Can capacity be 0?

**Locked: yes.** `capacity` may be 0 (HQ/merch). No dummy 1s.

### 4. Short codes for each building?

**Locked:** Dwinelle → `DWIN`, Wheeler → `WHLR`, VLSB → `VLSB`, Martin Luther King Jr. Building → `MLK`. **GPBB is out of scope.** Codes are **not** casually editable in the catalog UI (set at create only).

### 5. Who can see the catalog?

**Locked:** same Google as HQ, with `can_open_ops`. Catalog is not a third password. It lives on **`roomsdb.berkeley.mt`**, not as a tab on `ops.berkeley.mt/planner` or Saturday HQ. Room laptops and guests never see the catalog. Organizer view-only is optional later.
