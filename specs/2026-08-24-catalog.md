# Catalog (rooms kernel)

**Status**: Workshop draft — first module spec

Parent: [BMT 2026 architecture](2026-08-23-bmt-2026-architecture.md). Existing code: `buildings` / `floors` / `rooms` in Phase 1–2b. This spec is the **target** catalog for Nov 14, not as-built C4.

Correct slightly-off details here in workshop; do not reopen “day-of never writes catalog.”

## Problem

The capacity spreadsheet is the kernel of every other module. If HQ, volunteers, maps, and the allocator each invent their own DWIN155, we lose. The catalog must be easy to type in by hand, grow a new field without a deploy, and stay untouched on Saturday.

## Decisions (this spec)

| Topic | Decision |
| ----- | -------- |
| Who writes | Google **admin** only. Organizer is view-only. Day-of tools never `UPDATE rooms`. |
| Identity | User-editable **building code** + floor **label** + room **name**. Display `{code}{name}` → `DWIN155`. |
| Built-in facts | `capacity` (required integer ≥ 0). `is_active`. Optional `sort_order`. |
| All other facts | **Admin-defined fields** (number / text / yes-no), values per room. |
| Grid pollution | `appears_on_grid` default **true**. False = catalog + maps + volunteer targets, **not** an allocator column. Hedge for HQ/food/merch-in-a-room. |
| Codes | Editable mappings; uniqueness per org on `buildings.code` (when orgs exist; until 2c, globally unique as today). |
| Entry | **Manual** in `#/catalog`. No spreadsheet importer required for Nov 14. |
| Soft delete | `is_active = false` retires a room from pickers. Does **not** mean “closed today.” |
| Floor labels | Strings (`C`, `D`, `E`, `B`, `1`, `2`). Dwinelle v0 seed `1`/`2` must be corrected before map join. |

## Model

```text
buildings        id, code, name, address?, is_active, sort?
floors           id, building_id, label, sort_order
rooms            id, building_id, floor_id?, name, capacity,
                 appears_on_grid, is_active, sort_order?
room_field_defs  id, name, value_type (number|text|boolean), sort_order
room_field_values room_id, field_def_id, value (JSONB)
```

Until Phase 2c, field defs are global (one org in practice). After 2c they hang off `org_id`.

**Uniqueness:** `(building_id, name)` as today. Two “155”s in different buildings are fine. Aliases (Wheeler `22A + 22AA`) can wait for maps import; catalog name is one string until then.

**Capacity vs custom number fields:** the allocator and proctor-count heuristic use built-in `capacity` unless a field is explicitly chosen later (e.g. “guts capacity”). v1 heuristic = built-in `capacity`. Guts can be a custom field staff fill; wiring the heuristic to it is a later checkbox, not a new column type.

**`appears_on_grid`:** sheet room picker and bulk “all of Dwinelle D” skip false. Maps, volunteer assignment, public labels may still use the row. Timers never apply unless the **day plan** has a testing activity there (ops rooms should not get testing allocations).

Today’s `room_type` (`auditorium` \| `small` \| `large`) and `optimal_capacity`: **migrate** to custom fields (or drop) so we do not keep a second hardcoded taxonomy. Workshop: keep `room_type` one more semester as a custom field with those three options, or delete.

Today’s `tags` JSONB: unused for product; replace with field defs.

## Screens (admin)

- Building list / create / edit (code, name, active).
- Floors under a building (label, sort).
- Room list filterable by building/floor/active/appears_on_grid.
- Room form: name, floor, capacity, appears_on_grid, active, plus a **dynamic** section from field defs.
- **Field definitions** admin: add/rename/reorder fields (delete only if unused, or hide).
- Organizer: same lists, **no save**.

No day-of “closed” checkbox here.

## API (shape)

All `/api/v1`, admin write, session required.

- CRUD buildings, floors, rooms (as now, plus `appears_on_grid` and field values).
- CRUD `room_field_defs`; values on room PATCH as `fields: { "Guts capacity": 80 }`.
- Inactive room: cannot add to a **new** sheet column (existing Phase 2 deactivate rules). Already-imported day plans ignore catalog edits until re-import (day-of overlay, not this module).

JSON camelCase.

## Workshop questions (catalog only)

These are **only** about the rooms database UI and fields, not the grid, not day-of, not Figma.

### 1. Keep today’s `room_type`, or throw it away?

**What exists today:** every room must be one of `auditorium` / `small` / `large`. The grid uses that for a warning if you drop Puzzle on a tiny room. You already said almost everything except `capacity` should be a **user-created field**, so this hardcoded trio is the leftover exception.

**What this is asking:** when we switch to custom fields, do we:

- **A. Drop it** — no type dropdown unless you add a custom field named e.g. “Room type” yourselves; or
- **B. Seed it** — we pre-create a custom field with those three choices so old habits still work, but you can rename/delete it like any other field.

**Why it matters:** if we **keep it hardcoded**, we have two systems (built-in type + custom fields) and you cannot add “seminar” without a code change. If we **drop it and you still want the grid warning**, we need some other signal later. v1 can ship **no type warning** either way.

**Not asking:** Figma map colors (classroom vs bathroom). That is map `kind`, a different list.

**How to answer:** `A drop` or `B seed as a custom field` (and whether the grid should still warn on type mismatch).

### 2. `appears_on_grid` vs a `kind` dropdown?

**What this is:** some catalog rows should **not** become columns on the time×room allocator (HQ, food-in-a-classroom, merch). Volunteers and maps may still need those rows.

Two ways to say that in the form:

- **Boolean:** checkbox “Show on allocator grid” (`appears_on_grid`, default on). Simple. HQ is “a room with the box unchecked.”
- **Kind:** dropdown `classroom | ops | other`. Classroom → on the grid; ops/other → off. More words, easier to filter “all ops spaces” later.

They do the **same job** for Nov 14 (keep junk off the grid). Kind is slightly nicer if you will often filter HQ vs merch; the boolean is one click.

**Why it matters:** this is the cheap hedge so food/merch do not force a `Location` type before November. Picking one avoids building both.

**Not asking:** whether food in a hallway is a room at all (that can wait). Not asking Figma layers.

**How to answer:** `checkbox` or `kind dropdown` (and if dropdown, the labels you want).

### 3. Can capacity be 0?

**What this is:** built-in `capacity` is required and is the number the allocator / “how many proctors” heuristic will use. HQ or merch might have **no seats**. Options:

- **Allow 0** — merch = capacity 0; heuristic says 0 proctors unless you override.
- **Require ≥ 1** — then every HQ row needs a dummy like 1, which will **lie** in “87 / capacity” and proctor counts unless we also hide those rows from heuristics (`appears_on_grid` false helps the grid, not necessarily HQ’s capacity column).

**Why it matters:** a required positive capacity forces fake numbers into the kernel, which is how spreadsheets rot.

**Not asking:** guts vs testing capacity (those are custom fields). Not asking headcount of students who showed up.

**How to answer:** `0 allowed` or `must be ≥ 1` (and if ≥ 1, what dummy you want for HQ).

### 4. Short codes for each building?

**What this is:** labels look like `DWIN155` — `{code}{room}`. The code is what CSVs, Figma, and search will match. It is **not** the pretty name (“Valley Life Sciences Building”). You already said mappings are **editable**; we still need a **first** value so we do not invent `WHEE` vs `WHEELER` in seed data.

Tentative Nov 14 halls: Dwinelle, Wheeler, MLK, VLSB, GPBB.

**Why it matters:** changing a code later breaks imports. Editable means you can fix a typo; it does not mean we should guess MLK as `MLK` vs `ASUC`.

**Not asking:** floor letters (`C`/`D`/`E`). Not asking street addresses.

**How to answer:** a list, e.g. `Dwinelle → DWIN`, `VLSB → VLSB`, `Wheeler → ?`, `MLK → ?`, `GPBB → ?`. “Use the usual campus abbreviations and we will edit if wrong” is a valid answer.

### 5. Who can **see** the catalog (not edit)?

**What is already locked:** only **admin** (~3 Google accounts) can **change** rooms. Day-of never writes the catalog.

**What this is asking:** who may **open `#/catalog` and read** capacities and custom fields?

- **Admins only** — organizers do not see the room list in-app (they still see room names on the day plan / grid).
- **Admins + organizers** (view only) — the earlier sketch. Organizers can look up capacity without pinging an admin.
- **Anyone signed in** — including a future volunteer-manager role, if you add one.

Proctors (room-password laptops) should **not** get the full catalog admin UI.

**Why it matters:** capacity is not secret, but custom fields might include notes you do not want on a shared HQ laptop vs a volunteer. This is a read permission, not a write permission.

**Not asking:** who may import the day plan (admin). Not asking public guests (`live.berkeley.mt`).

**How to answer:** `admins only` / `admins + organizers` / `every Google staff account` (and whether volunteer PII ever belongs on this screen — it should not).
